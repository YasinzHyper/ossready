## [Unreleased]

### Added

- `ossready doctor --list` prints every check without auditing anything: its id, title, level, a one-line description, whether `--fix` can fix it (`yes`, `partial`, or `no`), what it looks at, and when a conditional check runs. `--list --json` prints `{ total, checks: [{ id, title, level, description, fixable, fix, looksAt, runsWhen, group? }] }`. It always exits `0`
- The check catalogue in `src/checks.ts` (`CHECK_CATALOG`, `checkInfo()`) is the single metadata source for every doctor check (id, title, level, description, fix support, what it looks at). `doctor` takes each check's id, label, and level from it, so reports, scores, and `--json` results are unchanged (results gain no fields)
- Generated reference docs: `docs/checks.md` (the catalogue as a table plus per-check details) and `docs/commands.md` (every command and option with examples). They are rendered by `src/docs.ts` from `src/checks.ts` and `src/cliSpec.ts` (the command and option definitions that `src/cli.ts` now registers with cac, so `--help` and the docs share one source) and written by `npm run docs:gen` (`scripts/gen-docs.mjs`), with no new dependencies. `docs/` and `scripts/` are not in the npm package
- `tests/docs-up-to-date.test.ts` fails when the committed docs differ from what the code generates (the message says to run `npm run docs:gen` and shows the first differing line; on GitHub Actions the expected file is also printed as notice annotations) or when Prettier would reformat the generated Markdown. `tests/doctor-list.test.ts` keeps the catalogue in step with doctor (order, labels, levels, groups, `FIX_FILES`) and covers `--list` and `--list --json`
- `ossready doctor` recommends up-to-date ossready-managed files with a new `managed-files` check. It runs `ossready sync`'s own comparison in-process (`runSync`, dry run, same inference and owner rules) and passes when every file that carries the ossready marker matches the current template rendering; otherwise it warns and lists the stale files with their `+added -removed` counts. Missing files and files without the marker never fail it, and it is skipped (not counted) when no file carries the marker. `--json` adds `managedFiles: { status: "checked", files: [{ path, status, managed, reason?, added?, removed? }], stale }` or `{ status: "skipped", reason }`. ossready itself now scores 30/30, and fresh scaffolds for npm, pnpm, Yarn, and bun still pass `doctor --strict`
- `ossready doctor --fix` applies the `ossready sync --write` update for stale managed files only (never `--force`, never `--add-missing`) and prints what it updated under "Updated stale ossready-managed files". `--dry-run` previews it and `--json` adds `fix.managedFiles.update`. The `workflow-actions` "Not fixed automatically" hint now points at `ossready sync --write` for ossready-managed workflows
- `ossready sync` also manages `.github/PULL_REQUEST_TEMPLATE.md`, which now starts with an HTML comment marker (`<!-- Managed by ossready — edit freely; … -->` and a blank line; GitHub doesn't render it and it is stable under Prettier), and `.editorconfig`, which starts with the `#` marker. `MARKDOWN_MANAGED_MARKER` and `withMarkdownManagedMarker()` live next to the YAML marker in `src/templates/managed.ts`, and `isManaged()` / `stripManagedMarker()` understand both forms. SECURITY.md and CODE_OF_CONDUCT.md stay unmarked because they embed the `--security-email` / `--coc-email` contacts, which can't be recovered from the repo (and SECURITY.md's supported-versions table is meant to be edited); CONTRIBUTING.md, SUPPORT.md, and AGENTS.md stay unmarked because they are meant to be rewritten per project
- `tests/doctor-managed-files.test.ts` covers a fresh scaffold passing, a stale managed workflow warning and being fixed by `--fix` (rerun passes), `--fix --dry-run`, unmarked customised and missing files left untouched, the skip case, `--json`, and the workflow-actions hint. `tests/sync.test.ts` covers the Markdown marker, the `.editorconfig` marker, unmarked community docs, a stale PR template update, opting out by deleting the marker line, and `--force` adoption
- README section on managed files: which files carry the marker, why the others don't, and how to opt a file out (delete the marker line)
- `ossready sync [directory]` brings the template-owned GitHub config files that `ossready init` generates up to date with the current templates: the workflows (`ci`, `release`, `publish`, `codeql`, `dependency-review`, `scorecard`, `stale`, `lock`), `.github/dependabot.yml`, and the Issue Forms (`bug_report.yml`, `feature_request.yml`, `config.yml`). README, LICENSE, `package.json`, the PR template, and source files are never touched. It is a dry run by default and reports each file as up to date, would update (with a unified diff, or a `+added -removed` summary with `--quiet`), missing (would create only with `--add-missing`), or skipped with the reason. It exits `1` when changes are pending, so it works as a CI check, and `0` when everything is up to date and after a successful `--write`. `--write` applies the changes, `--force` also updates unmarked files, `--json` prints `{ directory, write, options, files: [{ path, status, pending, written, reason?, added?, removed?, diff? }], pending, written, ok }`, and `--github-owner` / `--package-manager` override the inferred values. Templates are rendered by init's own `buildScaffoldFiles` with the values `doctor --fix` infers (`package.json`, lockfiles or `packageManager`, the `origin` remote through `src/utils/github.ts`). A fresh scaffold with no lockfile falls back to the setup steps in its managed `ci.yml`. Without an owner, owner-bound files (Issue Forms `config.yml`) are compared with the placeholder version, and a file that already names a real owner is skipped instead of being rewritten with `OWNER`. The diff comes from a small built-in line diff (`src/utils/diff.ts`), with no new dependencies
- Ownership marker for generated YAML: every template-owned workflow, `dependabot.yml`, and Issue Form now starts with ``# Managed by ossready — edit freely; `ossready sync` previews template updates (delete this line to opt out)`` (`src/templates/managed.ts`). `sync` only overwrites files that still start with it. Unmarked files are reported as `skipped (not managed by ossready …)` unless `--force` is given, and an unmarked file that matches the template exactly is flagged as safe to adopt with `--force`. The PR template, CODEOWNERS, FUNDING.yml, and the Markdown and community files stay unmarked
- `tests/sync.test.ts` covers the marker (on exactly the managed templates, for every package manager), the diff helper, up-to-date scaffolds for npm, pnpm, Yarn, and bun (exit 0), an outdated marked workflow (diff, exit 1, `--write` fixes it, rerun exits 0), `--quiet`, an unmarked file skipped and then overwritten with `--force`, `--add-missing`, `--json`, the no-owner behaviour, `--package-manager` overrides and validation, and lockfile precedence
- ossready dogfoods `sync`: `tests/dogfood.test.ts` asserts `ossready sync .` has nothing pending on this repo, and CI runs it on the repo, on every `scaffold-e2e` leg (npm, Yarn, pnpm, bun, after install so lockfile detection is exercised), on the no-owner scaffold, and in `packed-install`, whose `--help` check now also requires `sync`. ossready's own `ci.yml` has extra jobs, so it stays unmarked and is reported as skipped. `release.yml` and `dependency-review.yml` aren't used here and are reported as missing
- `tests/package-contents.test.ts` checks the npm package the way users get it, as a packed tarball: it builds, runs `npm pack --dry-run --json`, and asserts the tarball has the `bin` entry (`dist/cli.js`, with a `#!/usr/bin/env node` shebang), the compiled `.js` and `.d.ts` for every source file, `README.md`, `LICENSE`, `CHANGELOG.md` and `package.json`; that `main` / `exports` / `types` resolve to packed files and `engines.node` is set; that nothing outside `dist/` plus those docs is shipped (no `src/`, `tests/`, `.github/`, `tsconfig`, coverage, `.env` / `.npmrc` / keys); and that it stays under a size budget (400 KB packed, 2 MB unpacked, fewer than 300 files)
- New CI job `packed-install` (npm, Node 22, existing jobs unchanged): `npm pack` from a clean checkout, installs the tarball into a temp project, then runs the installed binary: `ossready --version` must equal the `package.json` version, `ossready --help` must list `init`, `doctor` and `badges`, and `ossready init --yes --name smoke --github-owner YasinzHyper` followed by `ossready doctor --strict` must pass in a temp directory. It uses the same `actions/checkout@v7` / `actions/setup-node@v7` pins and least-privilege `contents: read` permissions as the other jobs, with no npm cache
- CONTRIBUTING.md has a "Releasing" section covering the pack check, the `packed-install` job, and that publishing is maintainer-only (a GitHub Release, the Publish workflow, and the maintainer's `NPM_TOKEN`)
- `ossready init` writes the managed README badge block (`<!-- ossready:badges:start -->` … `<!-- ossready:badges:end -->`) right after the H1, built by the same code as `ossready badges` (the new pure `buildBadges()` in `src/commands/badges.ts`, used by `detectBadges()` and by the README template's `scaffoldBadgeBlock()`) from the scaffold's owner, repo name, package name, license, and workflows. Without an owner it has only the badges that don't need one (npm version / downloads and license), exactly what `ossready badges` prints. `ossready badges --write` on a fresh scaffold gives no diff, and the README still passes Prettier and every scaffold e2e leg (npm, Yarn, pnpm, bun, npm without an owner)
- `ossready doctor` recommends a current README badge block with a new `readme-badges` check: it passes when the root `README.md` has the markers and the block matches what `ossready badges` would generate, and warns when the markers are missing, the block is outdated, or only one marker is present. It is skipped (not counted) without a root README.md. `--json` adds `readmeBadges: { status, state, owner, badges, needsOwner }` or `{ status: "skipped", reason }`. The owner comes from `doctor --github-owner`, then `package.json` GitHub URLs, then the repo's own `origin` remote (the same sources as `--fix`). ossready itself now scores 29/29, and fresh scaffolds for npm, pnpm, Yarn, and bun pass `doctor --strict`
- `ossready doctor --fix` runs the same write as `ossready badges --write` for `readme-badges` when the owner is known (after the other files and `package.json` links are written, so a no-owner scaffold gets its CI, CodeQL, and Scorecard badges from `doctor --fix --github-owner <you>`). Without an owner it lists the check under "Not fixed automatically" with `ossready badges --write --github-owner <you>`; a half-marked README is left alone. A README that `--fix` creates gets the badge block too. `--dry-run` previews it and `--json` adds `fix.readmeBadges`
- `tests/doctor-readme-badges.test.ts` covers the skip case, scaffolds for all four package managers with and without an owner, scoped packages, missing / outdated / malformed blocks, `--fix` with and without an owner (idempotent, then `--strict`), `--github-owner` validation, and `--dry-run`. The init and no-owner tests assert the scaffolded block equals `ossready badges` output, the no-owner CI job checks the owner's CI badge lands in the README after `doctor --fix --github-owner example`, and `tests/github-owner-scaffold.test.ts` now isolates git config with `GIT_CONFIG_GLOBAL` / `GIT_CONFIG_NOSYSTEM`
- `ossready badges [directory]` prints a Markdown block of README badges: CI (GitHub's native badge for `.github/workflows/ci.yml`), npm version and downloads (shields.io; only when `package.json` has a `name` and isn't private), License (shields.io; from `package.json` `license` or the LICENSE file), OpenSSF Scorecard (shields.io; when `scorecard.yml` exists), and CodeQL (native badge; when `codeql.yml` exists). `--write` inserts or updates the block in README.md between `<!-- ossready:badges:start -->` and `<!-- ossready:badges:end -->` (right after the first H1 when the markers are missing) and is idempotent, so a second run gives no diff. `--dry-run` previews `--write`, `--json` prints the badges, URLs, owner, and repo, and `--github-owner` / `--repo <name|owner/name>` override the inferred values. The owner comes from the shared inference in `src/utils/github.ts` (target `origin` remote, parent `origin` remote, `git config github.user`); without one, the owner-bound badges are left out with a hint and `--write` exits 1 without touching README.md. ossready's own README badge block is generated by it, and `tests/badges.test.ts` covers detection, URLs, markers, idempotency, the no-owner and private-package cases, and the dogfooded block
- `ossready doctor` flags outdated GitHub Actions with a new recommended `workflow-actions` check. It scans `.github/workflows/*.yml|yaml` for `uses: owner/repo@ref` lines and reports each action pinned to an older major than ossready recommends, with its location (for example `actions/checkout@v4 → v7 (.github/workflows/ci.yml:12)`). Local `./` and `docker://` actions and unknown actions are ignored, commit-SHA pins are listed as info only and never fail, and the check is skipped (not counted) when there are no workflow files. `--json` adds `workflowActions: { status, files, outdated, shaPinned }` or `{ status: "skipped", reason }`. `--fix` stays report-only for it and lists it under "Not fixed automatically" with a hint to bump the pins or let Dependabot's `github-actions` ecosystem do it. ossready itself now scores 28/28, and fresh scaffolds for npm, pnpm, Yarn, and bun pass `doctor --strict`
- `src/templates/actions.ts` (`RECOMMENDED_ACTIONS`) is the single list of recommended action versions. `tests/action-pins.test.ts` now asserts the scaffold templates pin exactly these refs, so the templates and the doctor check can't drift apart. `tests/doctor-workflow-actions.test.ts` covers outdated, current, SHA-pinned, local, docker, unknown, and quoted pins, multiple files, line numbers, `--json`, `--fix`, the skip case, and the scaffold for all four package managers
- `ossready doctor` checks npm publish readiness when the audited directory has a `package.json`, using 8 recommended checks with stable ids: `pkg-name-version` (name + semver version), `pkg-description`, `pkg-license` (set, and matching LICENSE when it is recognisably MIT / Apache-2.0), `pkg-links` (`repository`, `bugs`, `homepage`), `pkg-engines` (`engines.node`), `pkg-files` (`files` allowlist or `.npmignore`), `pkg-entry` (`main` / `exports` / `bin` are relative, not `.ts` sources, and covered by `files`), and `pkg-publish-access` (`publishConfig.access` for scoped names). Failing checks carry an actionable `detail`. They are skipped, not failed, when there is no `package.json`, when it is `"private": true`, or when it is not valid JSON. `--json` reports each check plus `packageJson: { status, reason? }`. ossready itself now scores 27/27, and fresh `init --github-owner` scaffolds pass `doctor --strict` for npm, pnpm, Yarn, and bun
- `ossready doctor --fix` adds missing `package.json` `repository` / `bugs` / `homepage` when the GitHub owner is known (`--github-owner`, existing GitHub URLs, or the `origin` remote), keeping the file's indentation and never changing existing keys. The other publish-readiness checks stay report-only and are listed under `fix.skipped`. `--dry-run` previews the fields, and `--json` adds `fix.packageJson.add`
- `tests/doctor-package-json.test.ts` covers every check, the skip cases, `--json`, `--fix` / `--dry-run`, and the scaffold for all four package managers. The dogfood test asserts ossready's own `package.json` passes
- Scaffold `AGENTS.md`, the cross-tool instructions file for AI coding agents (Codex, Copilot, Cursor, Claude Code, Gemini CLI, and others). It covers the project overview, setup, and the build, test, coverage, lint, typecheck, and format commands for the chosen package manager (with `corepack enable` for Yarn), the Prettier / ESLint / EditorConfig code style, pull request and commit expectations pointing to CONTRIBUTING.md, and a security note pointing to SECURITY.md. Scaffolds also get a short `.github/copilot-instructions.md` that points GitHub Copilot to AGENTS.md
- `ossready doctor` recommends `AGENTS.md` (new `agents-md` check, now 8 required + 11 recommended), and `doctor --fix` writes `AGENTS.md` and `.github/copilot-instructions.md` using the detected package manager, never overwriting existing files
- ossready dogfoods its own `AGENTS.md` with the repo's real commands and guard tests; `tests/agents-scaffold.test.ts` covers the templates for npm, pnpm, Yarn, and bun, `init`, `doctor`, and `--fix`
- Interactive prompts for `ossready init`: in a terminal (stdin and stdout are TTYs, `CI` not set), init asks for each option not passed as a flag — project name, description, license, package manager, author, GitHub owner, Code of Conduct email, and an optional security email. Enter accepts the `[default]`, which is inferred from the target folder's `package.json`, lockfiles, or the launching package manager when possible. Invalid answers are re-asked (emails use the shared `--coc-email` / `--security-email` validation). Ctrl+C (exit `130`) and end of input (exit `1`) cancel before any file is written, and `--dry-run` works with prompts. Built on `node:readline/promises` in `src/prompts.ts`, with no new runtime dependencies
- `--yes` / `-y` for `ossready init` skips prompts and uses the defaults for omitted options. Non-interactive runs (pipes, scripts, CI) never prompt and behave exactly as before
- `tests/prompts.test.ts` drives the prompts with fake streams: defaults, overrides, invalid-answer re-prompts, EOF, Ctrl+C, default inference, `--dry-run`, and no partial writes. It also asserts that non-TTY, `--yes`, and `CI` runs never prompt
- `tests/no-owner-scaffold.test.ts` covers the no-owner path end to end (init without an owner → only `pkg-links` fails → `doctor --fix --github-owner example` → `doctor --strict` passes) plus every owner inference source, its order, and flag precedence, with git config isolated via `GIT_CONFIG_GLOBAL`

The `files` allowlist (`dist`, `LICENSE`, `README.md`, `CHANGELOG.md`) and the version are unchanged
- `ossready badges` now takes the owner and repo name from GitHub URLs in `package.json` (`repository`, `bugs`, `homepage`) before the git remotes, and falls back to the unscoped `package.json` `name` before the folder name. `detectBadges()` accepts `noParent` so `doctor` uses the same owner sources as `--fix`. The badge block now has a blank line around the badges so it is stable under Prettier; ossready's own README block is regenerated in that format
- Scaffolded READMEs no longer carry a CI badge pointing at `OWNER/<name>` or the "Replace `OWNER`" note when no owner is given; they get the npm and license badges, and init's no-owner next steps explain how to add the rest

### Fixed

## [0.2.0] - 2026-10-11

### ⚠ BREAKING CHANGES

- **Node.js 22.12+ is now required.** Node 18 and Node 20 are end-of-life and are no longer supported or tested: `engines.node` moves from `>=18` to `>=22.12`, and ossready's CI matrix moves from Node 18/20/22 to Node 22/24
- **Scaffolded projects target Node 22 and 24 too:** `ossready init` / `doctor --fix` now generate a `[22, 24]` CI matrix, `engines.node: ">=22.12"`, and `.nvmrc` pinned to `22` (was `[18, 20, 22]`, `>=18`, and `20`)

### Changed

- Upgrade to `cac` 7, `vitest` 5, and TypeScript 7 (supersedes Dependabot #31, #33, and #34, which failed on the Node 18/20 jobs or on TypeScript 7's build); `@types/node` now tracks the minimum supported runtime (22.x). TypeScript 7 no longer picks up `@types/node` implicitly, so `tsconfig.json` now lists `"types": ["node"]`
- Scaffolded projects get `vitest` and `@vitest/coverage-v8` `^5.0.3` (kept on the same version) and `@types/node` `^22.20.5`. The scaffolded `typescript` stays on `^5.7.2` because `typescript-eslint` does not support TypeScript 7 yet
- `tests/node-support.test.ts` keeps ossready's own CI matrix and `engines.node` in lockstep with the scaffold templates (npm / pnpm / bun)
- Scaffolded workflows now pin the current Node 24-based GitHub Action majors instead of the deprecated Node 20 ones: `actions/checkout@v7`, `actions/setup-node@v7`, `github/codeql-action/*@v4`, `actions/upload-artifact@v7`, `actions/stale@v11`, `actions/dependency-review-action@v5`, `pnpm/action-setup@v6` (still pnpm 9), and `softprops/action-gh-release@v3`. ossready's own workflows move to `actions/checkout@v7` and `github/codeql-action@v4` to match (supersedes Dependabot #35 and #36, which failed because the dogfooded `codeql.yml` drifted from its template)
- `tests/action-pins.test.ts` keeps scaffold templates and ossready's own Dependabot-maintained workflows on the same action versions, so a workflow bump that forgets `src/templates` now fails CI with an explicit message
- Scaffolded `SECURITY.md` links the real private advisory form (`https://github.com/<owner>/<name>/security/advisories/new`) when `--github-owner` is set, instead of `OWNER` / `security@example.com` placeholders
- `codeOfConductText()` falls back to the GitHub owner (or no contact) when the CoC email is empty, instead of rendering an empty `****`; `ossready init` still defaults `--coc-email` to `conduct@example.com`

### Added

- `--package-manager yarn` for `ossready init`, alongside npm, pnpm, and bun. Yarn scaffolds target modern Yarn (Berry) via Corepack: `package.json` pins `"packageManager": "yarn@4.18.1"`, `.yarnrc.yml` sets `nodeLinker: node-modules` (ESLint, Vitest, and TypeScript work without PnP), and `vite` is listed as a devDependency because Yarn does not auto-install Vitest's peer. Generated CI and publish workflows run `actions/setup-node` → `corepack enable` → `yarn install` (mutable via `YARN_ENABLE_IMMUTABLE_INSTALLS=false`, since no lockfile is committed; no cache) → `yarn <script>`; publishing still uses `npm publish --provenance`. README / CONTRIBUTING show `corepack enable` + `yarn` commands, and init's next steps include `corepack enable`. Invalid `--package-manager` values now list `npm | pnpm | yarn | bun`
- All scaffolds' `.gitignore` covers Yarn Berry state (`.yarn/*` keeping `patches`, `plugins`, `releases`, `sdks`, `versions`, plus `.pnp.*`); `.prettierignore` and the ESLint config ignore `.yarn` and `.pnp.*`
- `ossready doctor --fix` detects Yarn repos from `yarn.lock`, `.yarnrc.yml`, or the `packageManager` field in `package.json` (lockfiles for pnpm / bun still take precedence) and writes a Yarn CI workflow for them
- `tests/yarn-scaffold.test.ts`, yarn cases in the per-package-manager tests (scaffold-format, node-support, action-pins, lint / format / coverage / CI-hardening), and a `[npm, yarn]` matrix for the `scaffold-e2e` CI job that installs a fresh Yarn scaffold with Corepack and runs all of its scripts plus `doctor --strict`
- `--security-email <email>` for `ossready init` and `ossready doctor --fix`: when set, scaffolded `SECURITY.md` includes that address as a private reporting contact (alongside the GitHub advisory form when `--github-owner` is set). Omitting the flag keeps the previous owner-aware advisory-only / placeholder behavior — no fake default security email is invented for dogfood
- Shared email validation for `--coc-email` and `--security-email`: clearly invalid addresses are rejected with a friendly CLI error (non-zero exit) before any files are written

- `ossready doctor --fix` writes the files behind failing checks from ossready's own templates (never overwrites existing files; no `package.json` / `src` changes), then re-audits. Infers name, description, author, license, GitHub owner, and package manager from `package.json`, lockfiles, and the `origin` git remote, with `--github-owner`, `--author`, `--license`, and `--coc-email` overrides; `--dry-run` previews; `--json` adds a `fix` summary. `LICENSE` is only written when the license is known (MIT / Apache-2.0)
- `scaffold-e2e` CI job (Node 22): builds ossready, scaffolds a fresh project with `ossready init`, runs `npm install` there, then `format:check`, `lint`, `typecheck`, `test`, `test:coverage`, `build`, and `ossready doctor --strict`, so a template that breaks generated projects fails CI
